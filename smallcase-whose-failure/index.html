Whose failure is it?

When a partner’s Gateway conversion drops, the first question is always the same: our SDK, the broker, the investor, or the partner’s own integration? Answering it usually takes a ticket, logs from three systems and days of back and forth, while the partner assumes it’s Gateway. I built the diagnosis that answers it in a minute, using the error codes and order statuses Gateway already publishes, and sends each failure to whoever can fix it.

The short version, for the sample partner

    1 · The problem

    Every failed transaction looks like Gateway’s fault to the partner

    Gateway is how 250+ wealth players and financial institutions put investing inside their own apps. Partner adoption grows when transactions complete. When they don’t, the partner sees one thing: “it failed inside the smallcase flow”. The data to tell the causes apart already exists. Gateway documents its transaction error codes (1001 to 4006) and the order errorCodes brokers return. But a code isn’t an owner, and the same drop in conversion can come from five different places, each with a different fix:

    2 · The working tool

    A partner’s Gateway log in, every failure routed, a report out

    It loads with a fictional wealth app’s 30 days of Gateway transactions: about 16,000 attempts across six fictional brokers, on Android, iOS and web. The columns are the ones a partner already gets from SDK responses and webhooks. Upload your own CSV in the same shape; it runs in the browser and nothing is uploaded.

    Accuracy, honestly. Across 20 synthetic partners (308,952 transactions) it routed every failure to the owner I planted.     3 · What I would ship

    Four changes, ordered by how much partner pain they remove

    1. Integration health for every partner

      The same routing, as a page in the partner dashboard and a weekly email to the partner’s engineering lead. Partner bugs come with evidence and the exact fix, and broker and market failures are shown as “not yours”. That last part is what stops a partner blaming Gateway for a broker outage.

    2. Checks before the order screen

      Most investor failures are predictable. Check funds before a buy, since Gateway can already fetch funds. Prompt CDSL authorisation before a sell at brokers where it keeps failing. Offer AMO automatically after hours. Each one turns a rejection after login into a prompt before it.

    3. Broker incident detection

      Compare each broker’s connection-failure rate per hour with its own normal rate. During an incident, show a notice in the broker chooser and offer to place the order when the broker recovers. Alert broker ops before the first partner complains.

    4. Catch integration bugs in the sandbox

      Fail the integration checklist if a transactionId is reused, a smallcaseAuthId is saved for two users, or the webhook doesn’t answer. These are the bugs this tool finds in production; they’re cheaper to catch before go-live.

    4 · How we would know

    Partner completion and time to diagnose, not dashboard views

    Main measure

    Completion rate per partner, counting only transactions that got past the investor’s own choices (so investor drop-offs don’t hide integration bugs).

    Speed

    Time from a partner’s “conversion is down” ticket to a named cause. Today’s baseline comes from the support queue.

    Proof the report works

    Partner-side failures should fall within two releases of a partner getting the report. If they don’t, the report is being read and ignored, and the fix is in how it’s delivered.

    Guardrail

    False broker-incident alerts. One wrong alert to broker ops costs more trust than ten missed small ones, so the bar starts high and drops only with evidence.

    5 · What I don’t know

    • What exists internally. smallcase almost certainly monitors brokers and errors already. This is the partner-facing layer and the routing logic. I’d start by finding out what’s there and building only the gap.
    • The real mix of codes. My numbers are invented. The first week would be spent on real logs to see which owner actually dominates, partner by partner.
    • Broker-specific behaviour. CDSL authorisation and dormant-account rules differ by broker. The hotspot logic finds them from data rather than assuming them.
    • The order of the four changes. If most partners are well integrated, pre-checks in the SDK move more transactions than the health report does, and should go first.

    6 · How it’s built

    Gateway log (SDK responses + webhooks)→classify every transaction against the documented codes→7 pattern checks→owner · evidence · fix→partner report · reconcile list

    27 automated tests. They check owner routing against a known answer key (20 synthetic partners), each of the seven pattern checks, broker incidents on the right broker and hours with no false alarms, single codes against the docs (including the marginExceeded spelling the docs flag and unknown codes falling back safely), market hours, the reconcile list, the partner report, and messy exports with title rows, other header names and dd/mm/yyyy dates.

    Honesty notes. The partner, its users, the brokers and every transaction are invented. Broker names are fictional on purpose, so no real broker is implied to have had an incident.
