Supply Desk

The APM-toolkits job is measured on how many apps are live and how healthy they stay. This is the v1 of the machine behind that number: a scanner that reads an app's API spec and writes the launch brief, run on 32 real public specs, plus the pipeline, health rules and metrics I would run in the first 90 days.

Aditya Mathur · October 2026 · built for Composio's toolkits team

Read this first. I don't work at Composio and used no internal data. The 32 specs are real public OpenAPI files from the APIs.guru directory; they are snapshots and can lag the live APIs (one example below). Composio already supports most of these apps. The point is the intake machine, which matters most for the long tail. Scanning rules are deterministic and listed on the page; nothing is guessed by a model.

    Why the spec diff matters: the public Square snapshot I scanned has no webhook API, but Square's live docs list a Webhook Subscriptions API. Specs go stale, and a toolkit built from a stale spec is broken on day one. The weekly diff is the cheapest health check there is.

    SLA breaches by stage show where people, not automation, are the bottleneck. That is the trigger for hiring.

    6 · First 90 days

    Mapped to the JD's own goals

    Days 1–15Launch apps by hand, end to end, to learn where the time goes. Run the scanner on the open request list and sort it into lanes. Write the failure-classification rules against real error logs.
    Days 16–45Automate intake and QA: brief from spec, LLM-drafted tool descriptions with review, automated smoke runs. Repair queue for live toolkits, worked by severity.
    Days 46–75Supply, health and pipeline dashboards live. Weekly spec diff for the most-used toolkits. First SLA review.
    Days 76–90V1 playbook written: what agents do, what people do, when to hire. Readout on toolkits added, repaired and cycle time.
    Limits
    • Specs are public snapshots and can be stale or incomplete (Notion, ClickUp). The scanner reports what the spec says; a person confirms.
    • Classification is by rule on method, path and operation ID. It is deliberately cautious: some sandbox or simulation endpoints get flagged as money-moving.
    • It cannot see things outside the spec: Slack's Events API is configured in the app dashboard, so the scanner reports polling only.
    • Lanes and effort sizes are my first cut, to be recalibrated against real launch times.
