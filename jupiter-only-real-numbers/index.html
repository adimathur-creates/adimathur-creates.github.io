02 · The problem

Inside the team, a wrong answer costs a re-do. With customers, it costs money.

If a PM gets a wrong number in a draft PRD, someone catches it. If a customer asks “When is my bill due?” and gets the wrong date, they pay a late fee. If they ask what they spent on Swiggy and the answer forgets a refund, they stop trusting every number in the app. Your post lists three hard-won lessons. I turned each one into a design rule:

1“‘Sounds right’ isn’t good enough.”Tools compute, the model only speaks.Every amount, date and count comes from a query on the ledger. The model phrases it.
2If a number isn’t real, it doesn’t go in.A guard checks every claim before it ships.Any number, date or merchant in the answer that no tool produced blocks the answer.
3The boring parts matter more than the clever prompt.Evals, cost and honest failure come first.An eval set with release gates, a cost-per-answer model, and answers that say “I can’t see that.”

04 · The eval set

26 questions that decide whether this ships.

Each question has a gold answer computed from the ledger by separate code. Nine are money-critical, and those must all be right. Most cases have a trap: a pending hold, a refund, a period that isn’t a calendar month, a merchant that isn’t there, a request for investment advice, or a request for an OTP.

The right-hand set is constructed, not recorded from a model. Each trapped question gets the specific mistake its trap invites, and untrapped questions are answered correctly, so it isn’t a strawman. It exists to show the grader catching each type of failure. To score a real model, upload its answers below.

05 · Cost per answer

Don’t pay to send 120 days of transactions to the model.

The easy build pastes the customer’s history into the prompt and asks the model to work it out. It costs more, gets slower as history grows, and still gets the maths wrong. Tool-first sends the model only the question, then only the evidence.

Token prices are placeholders for a small model, so swap in your vendor’s. Token counts: 28 tokens per transaction row, a 700-token system prompt for the dump design, and two short calls (route, then phrase) for tool-first. The ratio matters more than the rupees.

06 · If I joined

The first 60 days, and the numbers I’d watch after launch.

  1. Weeks 1–2: choose the first job. Read-only questions about the customer’s own money: spending, bills, charges, rewards and subscriptions. No advice and no money movement in v1. Pull the real questions from support tickets and in-app search in Amplitude, the same sources your PRD agent already reads.
  2. Weeks 3–4: build the eval set from those questions, with gold answers from the ledger and a trap on every money-critical intent. Agree the release gates with Risk and Compliance before anyone sees a demo.
  3. Weeks 5–6: shadow mode. Run it behind support chat, compare it to what agents actually told customers, and fix the router, not the prompt.
  4. Weeks 7–8: launch to a small group behind a flag, with a one-tap “that number’s wrong” on every answer.
