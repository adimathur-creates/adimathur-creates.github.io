Audience Desk

One front door for segment requests. It reuses what the catalogue already has, runs the governance checks before anything ships, and turns what's left into a story the squad can pick up.

Aditya Mathur · October 2026 · Code

Read this first
  • I don't work at Tesco and used no internal data. The segment catalogue, filters and the 40,000 households below are synthetic, generated in your browser from a fixed seed.
  • Sizes are scaled to 24 million Clubcard households only so they read naturally. They are not estimates of Tesco's real audiences.
  • The problem comes from Tesco's own public job ads (section 1). The thresholds (minimum sizes, the 25% contact-pressure line, the sensitive-category list) are my proposals, written to be replaced by Tesco's real policy.
  • Everything on this page is deterministic rules, not a model. The same request always gets the same answer, and every answer says why.

1The problem, in Tesco's own words

Three public Tesco job ads describe the same product from different seats. Read together, they say segments and filters are a shared product with many requesters, and that quality, governance and adoption are the hard parts.

This role (APM, Bengaluru)
Support the management of behavioural segments and audience filters, keep them to data quality and governance standards, turn business requests into user stories and acceptance criteria, and grow adoption.
Head of Audience Performance (UK)
Set an "audience truth" standard so every segment, filter and trigger is measurable and compliant; build "air-traffic control" so customers aren't over-contacted; run a Planning Pod that prioritises audience requests.
Product Manager, Data & AI (Bengaluru)
Hands-on segmentation and rule-based audience creation; find pain points in how teams consume customer data; make products work for Insights, Marketing, Personalisation and Analytics.

Demand is rising: Tesco says it is investing in AI personalisation for its 24 million Clubcard households, opened an innovation lab with Adobe in April 2026, and began rolling out its AI meal planner in September. More personalisation means more audience requests reaching the same catalogue.

Where I'd expect it to break (my hypothesis, to test in the first month)

Near-duplicate segmentsA requester can't tell that "Lapsed bakery (8w)" already exists, so "Bread lapsers 6w" gets built. Definitions drift and two teams report different numbers for the same customers.
Governance found lateConsent, minimum size and sensitive categories get checked at activation, after the squad has already built the segment.
Vague ticketsA one-line Slack ask becomes a story with no definition and no acceptance criteria, and comes back for rework.
Adoption looks lowIf reuse isn't visible, the catalogue's best segments look unused while copies multiply. Nobody can say which segments to retire.

2Try the desk

Type a request the way a marketer would in Slack, or pick one. The desk reads it, finds who you mean in the synthetic households, compares that with every catalogue segment, runs six checks, and decides.

3Catalogue health

The same overlap maths, run across the catalogue itself. This is the weekly report I'd want as the APM: what to merge, what to retire, what's stale. The catalogue was built with planted problems, and the check finds them.

4How it runs

The page above is the engine. The agent runs the same engine file and uses Composio to listen and reply in Slack, file the Jira story and log every request to a sheet.

Why ComposioThe desk needs three tools a requester already lives in. Composio handles sign-in and permissions for all three through one SDK, so the desk is one engine file and a few lines of glue instead of three integrations.
Built to fail safelynpm run verify checks every tool name and argument against Composio's live schema and pins versions before anything goes live. The default mode is a dry run that prints the calls and touches nothing.
Tested8 request cases plus 5 rule checks run on every change. One test caught a real bug: "email about the new gluten-free bakery range" was adding Bakery to the audience. Words describing the campaign are now kept out of the targeting.

What I could not do: run it against a live Slack, Jira and Sheets workspace, because I don't have Composio connections for them. The tool names and argument names are my reading of Composio's toolkits; the verify script exists precisely so that a wrong guess fails loudly on day one rather than silently.

5How I'd measure it

MetricDefinitionWhy it matters
Reuse rate (main metric)Requests served from the existing catalogue (reuse, or reuse with filters) ÷ all requestsEvery reuse is a build the squad didn't do and a definition that didn't fork.
Time to audienceRequest posted → audience usable, median and 90th percentileWhat the requester feels. Reuse should be same day.
Late governance failuresAudiences that failed consent, size or sensitivity at activation, after buildShould fall to near zero once checks run at intake.
Duplicates createdNew segments with 90%+ household overlap with an existing one, per monthThe sprawl the desk exists to stop.
Story reworkDesk-filed stories sent back for unclear requirementsTests whether the generated acceptance criteria are actually usable.
Guardrail: wrong callsRequests where the requester or squad overrode the desk's decisionIf this rises, the matching rules are wrong. Review every override in the pilot.

6My first 90 days, if this were my product area

Weeks 1–4 · Learn
  • Sit with the PM's request queue and read last quarter's requests.
  • Interview 8–10 requesters across Marketing, Insights, Tesco Media and Rewards.
  • Label every past request as reuse, extend or build. If reuse is under 20%, my hypothesis is wrong and the desk isn't the priority.
Weeks 5–8 · Pilot
  • Run the desk read-only in one team's channel. It recommends; people still triage.
  • Measure how often it agrees with the human call.
  • Merge the duplicates the health report finds, with owners' agreement.
Weeks 9–12 · Ship
  • Turn on Jira filing for extend and build.
  • Make time windows a setting on the most-copied segment families.
  • Put reuse rate and late failures on the team's monthly product review.

7What would prove me wrong

  • Requests may already come through a structured form in the audience tool, not free text. Then the parsing step is unnecessary and the value is only in matching and checks, which belong inside that form.
  • Overlap on a sample isn't overlap on 24 million households. On real data, matching should run on the live segment tables, and small segments need exact counts, not samples.
  • Tesco's privacy rules will differ from mine. The sensitive list and size floors are placeholders for the real policy, owned by privacy and legal, not by the product team.
  • A model could read requests better than my rules. I'd only add one with the rules kept as the final check, so a model can suggest but never decide.
